### R1 兼容边界

- EVM 使用 `log:<index>`，Solana 使用解析后稳定的 `instruction:<index>`，TON 使用 `inbound:<LT>`，Aptos 使用扫描器相同的转账键。哈希别名规范化和网络隔离保留。
- 人工核验前只提前拒绝没有事件回执的历史支付；已有事件的交易必须先从 RPC 识别所选转账。核验后仍在结算事务中再查，不能仅靠 RPC 前检查防重。预检查读取也受 `CollectionMu` 保护，避免把“回执读取前、订单提交后”的混合快照当成旧支付。
- TRON 人工核验暂不把 receipt log 编号冒充扫描器的 `contract:0`。这类人工支付及其他旧版缺少事件编号的支付继续采用保守的交易级防重。这是兼容限制，不能宣称所有链的人工批量转账均可拆分入账。
- 升级不会自动重开旧版已经保存的 `duplicate_payment` 等异常。历史资金需核对，不能删除回执来强行重试。

### R3 状态与迁移边界

`provider_orders` 新增 `request_amount`、`return_url` 两个普通字符串字段，由现有 AutoMigrate 创建。首次恢复旧记录时从持久化金额建立请求快照，不按当前精度再次舍入。通知按冻结金额进行十进制校验，不按当前全局精度放宽金额。

创建请求前提交本地支付目标，便于早到通知正确结算；HTTP 不持有结算锁。创建响应不能覆盖已支付或已关闭状态，也不能更换已绑定的供应商订单号。已过期/手动关闭/其他通道获胜的订单不能借重试复活。旧版因创建失败而关闭的子单，仅在主单仍可支付、原期限有效且没有付款凭据时恢复。

本地复用 `unique_id` 已证明；**真实 OkPay 是否保证相同 unique_id 的创建幂等、响应丢失后能否返回原支付链接，本次没有供应商契约/联调证据**。没有新增后台自动无限重试；恢复由用户再次选择通道触发。联调期间应固定供应商账户、接口和回调配置。

### R5 联调范围与发现依据（已更正商家路径）

没有用手写模拟商家代替业务逻辑：测试在另一个进程编译并运行商家 `RequestEpay`、`EpayNotify` 和余额/支付事实模型；网关运行真实注册路由和回调构造函数。使用临时 SQLite、模拟 Redis，网关的商家回调传输仅允许固定测试主机并映射到本机端口。链上付款证据在已确认转账边界注入，不连接真实链。

链路：商家充值请求 → 签名 POST 到网关 → 商家保存支付链接和充值单 → 网关主/子通道结算 → 真实签名回调 → 商家余额与订单核对 → 重复/并发回调 → 迟到 CLOSED → 同步返回原商户单号。

| 场景 | 网关结果 | 商家最终结果 |
| --- | --- | --- |
| 原通道足额 5 | 成功 | 原单 5 美元，只加一次额度 |
| 切换子通道少付 3 | 主单成功、实付 3 | 原单 3 美元，只加一次额度 |
| 切换子通道超付 7 | 主单成功、实付 7 | 原单 7 美元，只加一次额度 |
| CLOSED 后发现截止前实付 3 | 过期恢复成功 | 旧副本曾复现未入账却 ACK；正确分支已有恢复逻辑，继续验证 success、入账 3 美元 |

配置使用网关支持的 `usdt.tron` 支付方式和 `currency=usd`。未验证任意自定义 type/配置组合；前端浏览器页面、登录鉴权、真实 RPC/OkPay 不包含在这组 HTTP 联调内。

复审从建单到商家余额沿同一流程检查，没有以单个反例通过代替全链路结论。

| 阶段 | 已验证的正常/失败/重试 | 并发与持久化证据 | 剩余边界 |
| --- | --- | --- | --- |
| 建单、金额/地址占用 | 精度与最低额快照；失败不占用；选币写失败回滚 | 地址竞争、父子单一赢家、固定独占截止时间 | 真实容量与数据库等待时间 |

| EVM/TRON 扫描 | 确认数、日志/区块身份、停滞和缺失响应、失败不前移游标 | 启动边界冻结、恢复持久化游标、WS/补扫重放去重 | 真实 RPC 历史完整性 |
| Solana/Aptos 扫描 | 分页、资产、原始金额、响应不完整/限流后恢复 | checkpoint、初始边界、多事件分别入账 | Aptos 新用例从转账入口进入，不冒充新增 indexer 端到端验证 |
| TON 扫描 | 原生币/Jetton 最低额、分页失败恢复、节点停滞 | 分片拆分/合并和历史追溯、重复入账防护 | 主网节点样本 |
| 历史归属/结算/过期 | 原截止前迟扫恢复；手动关闭不复活；订单/receipt 写失败回滚 | 旧款不释放新锁；真实进程在 receipt 写入后、提交前退出；提交后退出；重新处理只留一份 receipt，地址释放正确 | 全服务双数据库及游标的组合 kill/restart |
| 人工补单 | 资产、收款方、金额、时间和历史归属；失败修正后重试 | 人工/自动同事件一次，不同事件互不误拦；事件回执和结算原子提交 | TRON/历史无事件证据的保守交易级限制 |
| 回调/同步返回 | 商户身份、实付金额、签名、ACK/退避、公平调度、失效证据拒发 | 旧 CLOSED ACK 不能确认新 SUCCESS；持久化回调重读；商家并发重复通知一次入账 | 整个应用崩溃、商家已入账但网关未记 ACK 的完整部署恢复 |
| 商家入账/异常处理 | 普通充值实际金额与原金额分离；支付事实、额度事务回滚 | CLOSED → SUCCESS、SUCCESS 后迟到 CLOSED、重复签名事实 | 历史已错误 ACK 的订单须主动对账、重发 |

## 真实依赖／线上数据才能确认

- 启用 RPC 的历史、索引完整性、鉴权/限流和故障切换。模拟节点不能证明真实节点的“成功响应”没有遗漏转账。
- OkPay 商家账户配置、签名协议与 unique_id 幂等契约，及真实支付后的通知时序。启用该通道前须真实供应商或其沙箱联调；禁用时应明确从发布范围移除该入口。
- 旧版已经跳过的扫描区间、错误 `duplicate_payment` 异常，以及商家已错误 ACK 的“网关成功/商家过期”充值，需要线上账目与链上证据核对。升级本身不会主动找出并补发所有这些历史订单。
- 实际负载、扫描落后量、数据库锁等待与恢复速度，及部署时钟偏差。先等价预发布验证，再小流量观测。
