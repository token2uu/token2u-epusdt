# Solana RPC 扫描限流

单实例默认每 15 秒触发一次调度，按地址活跃度选择本轮钱包，最多并发扫描 2 个钱包。所有 Solana HTTP
请求共用每秒 2 次的预算（包含分页、交易详情、健康检查和 HTTP 重试），不允许
并发突发。已有一轮未完成时跳过新的触发，不积累扫描任务。

这些默认值在已有部署没有配置新键时同样生效。可在应用 `.env` 中配置，重启应用生效：

```dotenv
solana_scan_interval_seconds=15
solana_idle_scan_interval_seconds=300
solana_recent_activity_seconds=600
solana_scan_concurrency=2
solana_rpc_requests_per_second=2
```

请求频率支持小数；非正数或非有限数使用默认值 2。进程内总预算不会因添加多个
节点而增加；多副本/其他共用出口 IP 的服务需要单独分配预算。

## 按地址活跃度调度

存在未过期待支付订单的地址每个调度周期扫描；最近 10 分钟内分配、释放、更新
过订单，或产生到账记录的地址也保持该频率。其余地址默认每 5 分钟扫描一次，
继续发现迟到付款及异常到账，不会因为没有待支付订单而停扫。冷地址间隔不得
小于调度间隔，配置非正数时使用默认值。按默认值，持续空闲地址的签名查询
频率由每小时约 240 次降为约 12 次，约减少 95%；分页和交易核验按实际需要执行。

新启用地址及进程重启后的第一轮立即扫描，继续使用原有持久化签名游标。
首次建立游标时，默认回看订单有效期加 5 分钟；存在更早创建的待支付订单时，
回看至该订单创建时间。钱包及各 ATA 的初始边界在发出首个请求前全部保存，
失败重试和重启不会缩短已保存的范围。
订单活动查询失败时，本轮保守地扫描全部地址。创建订单会在下个调度周期唤醒对应
地址，不必等待冷地址间隔。区块高度统计在有地址需要扫描时执行，最多每分钟
一次。上述时间是调度目标；RPC 限速、退避及上一轮未结束会使实际到账发现延后。

收到 HTTP 429 时，当前请求立即停止重试，对该端点设置共享冷却时间：优先
遵守 `Retry-After` 秒数或 HTTP 日期，没有有效值则冷却 30 秒。冷却期间新请求
直接返回限流错误，不访问节点。通用扫描路径立即尝试其他符合用途/健康状态的
节点，不等待普通故障累计达到切换阈值。通用扫描的 5xx/网络失败也在当前请求
内切换，每个节点尝试一次，不在故障公共节点上连续重试。原始直连调用仍保留
有界重试，每次尝试同样经过总限速器。冷却不会清除或推进支付扫描游标。

可将付费节点标记为 `paid_fallback`，实现公共优先及付费兜底，详见
[公共节点优先与付费回退](rpc-fallback.md)。普通请求默认超时为 5 秒，付费
兜底为 10 秒，均不超过调用路径原有超时。所有节点失败时仍保留游标。

## 历史签名不存在时的处理

`getSignaturesForAddress` / `getTransaction` 返回 JSON-RPC `-32020`
（历史交易或游标签名不可查询），或 `getTransaction` 返回 `result: null`
（该节点在请求的确认级别下暂时查不到交易）时，当前请求立即尝试其他符合用途、健康状态的
节点。缺少该段历史不等同于整台节点故障，不再依赖会被其他钱包成功请求清零的
节点级失败计数。

同一端点、方法、完整参数（含钱包、`until` / `before`）及鉴权头的失败查询，按
30 秒、1 分钟、5 分钟、15 分钟退避，之后最多每 15 分钟重试一次。同一查询的
并发请求合并；冷却期间不发送 HTTP 请求，不反复输出错误级日志。其他钱包、
新的游标或不同节点可以照常查询；仅该端点同一查询成功才清除其退避。

所有候选节点都无法读取时，扫描保留原游标及首次扫描时间下界，等待历史数据恢复
或替换能提供所需历史的节点。恢复后继续补扫并使用既有到账记录去重；不会把失败
查询当成空结果，也不会删除游标或跳到最新交易。持续出现 `history unavailable`
时，应按日志中的钱包和节点核对历史可用性，不应手工跳过尚未核对的付款区间。

查询退避保存在进程内，重启会重新探测，持久化支付扫描进度不受影响。此策略专门
处理 `-32020` 和交易详情 `null`，不会因此冷却整台节点或把其他钱包请求转到付费节点；
HTTP 429 仍使用上面的端点限流冷却，普通网络故障仍保留节点级
切换策略。

签名列表的校验和扫描共用大小写敏感的解析规则。响应顶层或签名条目包含重复字段
（包括转义后的同名字段）或大小写冲突时，拒绝该响应并尝试备用节点；所有节点都失败
则保留游标，避免错误状态覆盖导致跳过真实入账。

签名查询的 `limit` 只是每页上限。节点返回较短的非空页时，继续使用 `before` 翻页，
直到空页或首次扫描的时间下界；不会仅因不足 1000 条就推进游标。同一账户的分页若
重复返回已读签名（包括页内重复），拒绝该响应并尝试备用节点，避免循环扫描。
任何后续页失败且无可用备用节点时，整轮保留旧游标。正常短页继续走公共节点，
不会仅因页大小较小而转到付费节点；完整扫描通常会多一次确认结束的空页查询。

## 更换生产 RPC

在后台 RPC 节点管理添加 Solana 主网 HTTP 端点，用途设为“通用”或“通用+补单”。
应验证实际的 `getSignaturesForAddress`、`getTransaction` 和所需历史交易查询，
不能只依赖健康检查。需要使用带鉴权的完整 URL 时，只在受保护后台配置，勿
提交到仓库或粘贴到公开日志。可以额外配置另一供应商作为备用。

根据供应商实际的总请求、单方法、历史查询和月度额度提高上述预算；不要仅凭
节点响应快就调高。公共节点可能继续受到共享 IP/服务端负载限流，本修复不能
保证公共节点的可用性。

## 验证与恢复

观察 `[SOL] fetch signatures owner=… account=…`、429 冷却/节点切换日志及到账
记录。请求受限时游标保留，恢复后继续处理。已超时订单仍遵守现有异常到账
规则，需要按交易哈希核对；本修复不自动把超时订单改为成功。
